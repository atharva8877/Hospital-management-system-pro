HOSPITAL MANAGEMENT PATIENT ALERT SYSTEM
PROJECT DIAGRAMS (PLAIN-TEXT CHARTS)

Scope
-----
The ESP32 reads four physical buttons, updates an ILI9341 display, and sends
alert lines over serial. The optional PC service (app.py) reads serial data,
sends Telegram messages/audio, optionally starts Twilio calls, and plays
audio on the PC. The TFT menu is display-only; its drawn buttons are not
touch controls. The optional MAX98357A bedside speaker is not implemented.

9. SIGNAL PROCESSING PIPELINE DIAGRAM
-------------------------------------

  INPUT STAGE          FIRMWARE EVENT STAGE       TRANSPORT / PC STAGE
  -----------          --------------------       --------------------

  Button open          digitalRead(GPIO)
  switch               INPUT_PULLUP enabled
      |                       |
      |              released reads HIGH
      |              pressed-to-GND LOW
      |                       |
      +---------------------->v
                       +---------------------+
                       | Compare current     |
                       | pressed state with  |
                       | saved buttonState[] |
                       +----------+----------+
                                  |
                       Is LOW and was released?
                         | No             | Yes
                         |                v
                         |     Save state as pressed
                         |     Print "Button pressed: <TYPE>"
                         |     Return its array index
                         |                |
                         |                v
                         |     Map buttonPins[] index to alertNames[]
                         |                |
                         |                v
                         |     Check millis() - lastAlertMs >= 500
                         |       | No             | Yes
                         |       v                v
                         |     Suppress       Update lastAlertMs
                         |     transmission   Serial.print("ALERT:")
                         |                    Serial.println(TYPE)
                         |                         |
                         |                         v
                         |                TFT "SENT!" -> 2 sec delay
                         |                redraw menu -> 150 ms delay
                         |                         |
                         |                         v
                         |              +------------------------+
                         +------------->| USB serial 115200 OR   |
                                        | Wokwi RFC2217 socket   |
                                        +-----------+------------+
                                                    |
                                                    v
                                        app.py reads serial line
                                        decode UTF-8, strip whitespace
                                        require "ALERT:" substring
                                                    |
                                                    v
                                        Parse alert kind and route:
                                        EMERGENCY -> two Telegram IDs
                                        other types -> caregiver ID
                                                    |
                              +---------------------+------------------+
                              |                     |                  |
                              v                     v                  v
                     Telegram text/audio    optional Twilio     PC TTS playback
                     five waves; 2 sec      outbound call       initial alert
                     between waves

  Released-to-pressed state detection ensures a held button does not keep
  emitting events. The 500 ms gate is a shared cooldown. The 150 ms delay is
  an additional pause after a handled input; this code does not use a
  dedicated timer-based or hardware debounce filter.

  This is digital input/event handling, not analog sensor filtering. The
  current firmware does not implement a separate sampled debounce/filter
  algorithm.


10. ALGORITHM FLOWCHART (BUTTON-TO-ALERT IMPLEMENTATION)
--------------------------------------------------------

  (START)
     |
     v
  [Initialize buttonPins[] and alertNames[] arrays]
     |
     v
  [For i = 0,1,2,3 in array order]
     |    i=0 GPIO32 EMERGENCY
     |    i=1 GPIO33 WATER
     |    i=2 GPIO14 FOOD
     |    i=3 GPIO25 WASHROOM
     v
  [Read pin: isPressed = (digitalRead(pin) == LOW)]
     |
     v
  <Is isPressed true?>
     | No                              | Yes
     v                                 v
  [Set buttonState[i]=false]   <Was buttonState[i] false?>
     |                            | No             | Yes
     |                            v                v
     |                     [Button held;       [Set buttonState[i]=true]
     |                      no new event]      [Print button label]
     |                            |                |
     |                            |                v
     |                            |       [Return alert index i]
     |                            |                |
     |                            |                v
     |                            |       [Call triggerAlert(name)]
     |                            |                |
     |                            |                v
     |                            |       [now = millis()]
     |                            |                |
     |                            |                v
     |                            |       <now-lastAlertMs < 500?>
     |                            |          | Yes           | No
     |                            |          v               v
     |                            |      [Return;      [Update lastAlertMs]
     |                            |       no ALERT]          |
     |                            |                          v
     |                            |                  [Print ALERT:<TYPE>]
     |                            |                          |
     |                            |                  [TFT clear + SENT!]
     |                            |                          |
     |                            |                  [Delay 2000 ms]
     |                            |                          |
     |                            |                  [Redraw menu]
     |                            |                          |
     +----------------------------+--------------------------+
                                  |
                                  v
                       [Delay 150 ms after detected input]
                                  |
                                  v
                       [Return to loop; print STATUS
                        every 2000 ms when due]
                                  |
                                  +----> scan again

  IMPORTANT BEHAVIOR:
  - The button scan order is the array order above, not the visual menu order.
  - buttonState[i] resets only after that pin is read released (HIGH).
  - lastAlertMs is shared by all four buttons; rapid successive requests can
    be suppressed during the cooldown.
  - As coded, lastAlertMs starts at zero, so a button press during the first
    500 ms after boot is also inside the cooldown window.
  - triggerAlert delays for 2 seconds before the loop can scan buttons again.
